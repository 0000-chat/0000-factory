# 0000 Factory

0000 Factory is a standalone tracker engine and viewer. It reads an
explicitly selected, data-only repository and writes generated views and
browser artifacts to a separate output directory. A fresh checkout contains
the engine, its schemas, and synthetic examples; site-owned settings, real
task records, identities, deployment values, and provider credentials remain
external.

The first-party engine is licensed under AGPL-3.0-only. See LICENSE and
NOTICE for the license boundary and third-party notices.

## Prerequisites

Use Node.js 26.3.1, Bun 1.3.14, and the `setsid` utility. Install the frozen
dependency graph and the Chromium browser used by the acceptance suite:

~~~sh
bun install --frozen-lockfile
bun x playwright install chromium
~~~

Run the local gate with an external temporary parent. The check owns one
unique child process group, passes all fixture and output paths explicitly,
and verifies that the group and its descendants have exited before removing
the owned temporary child:

~~~sh
TMPDIR=/absolute/path/to/factory-check-cache ./scripts/check
~~~

The public privacy check can also be run on its own:

~~~sh
./scripts/privacy-check
~~~

## Explicit engine and data roots

Every engine command takes --engine-root ENGINE, --data-root DATA,
--settings SETTINGS, and, for commands that write artifacts, --out OUTPUT.
DATA is a separate data-only checkout. SETTINGS is inside that checkout, and
OUTPUT must be separate from both inputs. The engine rejects an input data root
nested inside the engine.

The root example is generated by tests/helpers/fixture-data.mjs. Copy it to
an external data directory before using it:

~~~sh
ENGINE="$PWD"
EXAMPLES="$(mktemp -d)"
mkdir "$EXAMPLES/root"
cp -R examples/root/. "$EXAMPLES/root/"
DATA="$EXAMPLES/root"
SETTINGS="$DATA/settings.json"
OUT="$EXAMPLES/root-output"

node tooling/tracker/cli.mjs build \
  --engine-root "$ENGINE" --data-root "$DATA" \
  --settings "$SETTINGS" --out "$OUT"
node tooling/tracker/cli.mjs check \
  --engine-root "$ENGINE" --data-root "$DATA" \
  --settings "$SETTINGS" --out "$OUT"
bun tracker/viewer/tooling/build.mjs \
  --engine-root "$ENGINE" --data-root "$DATA" \
  --settings "$SETTINGS" --out "$OUT"
~~~

The nested example keeps its settings, asset, and tracker files under the
literal tooling/project-tracker folder. Use the same explicit commands with
the nested settings path:

~~~sh
mkdir "$EXAMPLES/nested"
cp -R examples/nested/. "$EXAMPLES/nested/"
DATA="$EXAMPLES/nested"
SETTINGS="$DATA/tooling/project-tracker/settings.json"
OUT="$EXAMPLES/nested-output"

node tooling/tracker/cli.mjs build \
  --engine-root "$ENGINE" --data-root "$DATA" \
  --settings "$SETTINGS" --out "$OUT"
node tooling/tracker/cli.mjs check \
  --engine-root "$ENGINE" --data-root "$DATA" \
  --settings "$SETTINGS" --out "$OUT"
bun tracker/viewer/tooling/build.mjs \
  --engine-root "$ENGINE" --data-root "$DATA" \
  --settings "$SETTINGS" --out "$OUT"
~~~

The command-line help forms are:

~~~sh
node tests/helpers/fixture-command.mjs --help
node tooling/tracker/cli.mjs --help
bun tracker/viewer/tooling/build.mjs --help
~~~

The fixture helper also provides disposable synthetic commands for
tracker-build, tracker-check, tracker-validate, tracker-archive, viewer-build,
and viewer-dev. It never imports or writes application source into the
generated data directory.

## Data and deployment boundary

Examples use reserved .test domains and email addresses, synthetic
identities, fake repositories and branches, disabled publishing, and
unconfigured Access. Tests that exercise ready Access or simulated publishing
generate their own short-lived credentials and use fake transports. Real site
settings and production records are outside this repository.

Generated assets, Worker configuration, runtime configuration, manifests, and
viewer bundles belong to OUTPUT. The repository includes no deployment or
publishing command. Do not add a production checkout, provider token, browser
report, screenshot, generated output, or private log to a change.

## Proposed schedule dates

Task frontmatter may carry paired `proposed_start` and `proposed_end` dates
alongside the approved `planned_start` and `planned_end` fields. An optional
`proposed_schedule_kind` labels the proposal as `span` (a whole-task range),
`slice` (a partial-work window), or `checkpoint` (one proposed date). A
checkpoint must use the same value for both proposed endpoints. Proposed dates
are scheduling suggestions: they remain separate from planned dates, forecasts,
approval state, and approval digests, including when an accepted task carries a
later proposal. The Gantt renders them with proposed labels and styling.

## Development commands

The engine's package scripts create temporary synthetic data roots:

~~~sh
bun run tracker:build
bun run tracker:check
bun run tracker:validate
bun run tracker:viewer:routes:check
bun run tracker:viewer:typecheck
bun run tracker:viewer:build
bun run test:tracker
bun run test:tracker-viewer
bun run test:tracker-hosting
bun run test:tracker-ui
~~~

Pull requests must preserve the lockfile and the three pinned LiveStore
patches, keep executable code in the engine, and keep site-owned data in the
external repository.
